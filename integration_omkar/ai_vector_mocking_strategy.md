# SwipeX Milestone 3 — AI, Vector DB & Storage Mocking Strategy
**Role:** Intern 5 — Platform, Testing & Deployment  
**Scope:** Milestone 3 (Day 1 & Day 2)  
**Target Architecture:** Free, Offline, Deterministic, Zero-Cost Test Automation

---

## 1. Executive Summary & Objective

In SwipeX Milestone 3, the platform introduces:
1. **Object Storage (MinIO)** for resume document binaries (PDF/DOCX).
2. **Text & Skill Extraction Pipeline** (pdfplumber, python-docx, spaCy).
3. **Vector Database (ChromaDB)** for storing dense embeddings of job descriptions and resumes.
4. **Semantic Similarity & ATS Scoring Engine** (sentence-transformers / embeddings).
5. **AI Resume Suggestions Engine** (LLM-based or template-based suggestions).

Running automated continuous integration (CI) tests against live external LLM APIs (e.g., OpenAI) or loading heavy PyTorch embedding models (500MB+ per test run) creates:
- **Flakiness & Non-Determinism:** Network timeouts, model temperature variability, and API rate limits.
- **Financial Cost:** Accrued token fees on paid API keys.
- **Resource Heaviness:** High CI runner memory usage and prolonged test execution times.
- **Security Hazards:** Accidental exposure or dependency on private API keys in CI runners.

### Core Rule: Real System vs. Automated Test Isolation
> [!IMPORTANT]
> **Real functionality is NEVER replaced by mocks in application source code.**  
> Real implementations (MinIO S3 clients, ChromaDB persistent collections, sentence-transformers, live pipelines) are reserved for local multi-container development and Day 4–5 integrated testing inside `docker-compose.dev.yml`.  
> Mocks are **strictly scoped to automated test suites (`pytest`)** via dependency injection, monkeypatching, and fake service adapters.

```
REAL SYSTEM (Dev / Integration via Docker Compose)
    │
    ├── Resume Files     ──► MinIO Container (:9000 API, :9001 Console)
    ├── NLP Extraction   ──► spaCy / pdfplumber Pipeline
    ├── Embeddings       ──► sentence-transformers (all-MiniLM-L6-v2)
    ├── Vector DB        ──► ChromaDB Container (:8004 host -> :8000 container)
    └── Suggestions      ──► Template Generator / Optional Fallback LLM

AUTOMATED TEST SUITE (Fast, Deterministic, 0-Cost CI)
    │
    ├── Storage Call     ──► FakeStorageService (in-memory BytesIO / dict)
    ├── Embedding Call   ──► Deterministic FakeEmbeddingService (hash-derived 384-d vector)
    ├── Vector Search    ──► FakeVectorStore (in-memory cosine similarity dictionary)
    └── LLM Suggestions  ──► Static Mock Suggestion Provider (deterministic JSON schema)
```

## 2. Mocking Architecture Layers

### Layer A: Object File Storage (MinIO / S3)
* **Real System Implementation:**  
  Clients talk to MinIO over S3 protocol (`boto3` or `minio-py`) targeting `http://minio:9000` with bucket `swipex-resumes`.
* **Automated Test Mock:**  
  `FakeStorageService` stores file payloads in an in-memory dictionary `Dict[str, bytes]`.
* **Characteristics:**
  * Zero socket I/O overhead.
  * Instant teardown after each test.
  * Simulates upload (`put_object`), retrieval (`get_object`), metadata check (`head_object`), and intentional error conditions (`StorageError` to test TC-RES-14).

### Layer B: Embedding Generation (sentence-transformers)
* **Real System Implementation:**  
  `sentence-transformers` generates 384-dimensional dense vectors (`all-MiniLM-L6-v2`).
* **Automated Test Mock:**  
  `FakeEmbeddingService.embed(text: str) -> List[float]` produces a deterministic, unit-normalized float vector of length 384 generated by a seeded SHA-256 hash of the input text string.
* **Benefits:**
  * Same text always returns the identical numerical vector ($sim(A, A) = 1.0$).
  * Orthogonal text yields predictable cosine similarity without downloading 400MB PyTorch weights.
  * Execution time: < 0.1ms per embedding.

### Layer C: Vector Database (ChromaDB)
* **Real System Implementation:**  
  ChromaDB client connects to `http://chromadb:8000` with persistent storage in `/chroma/chroma`.
* **Automated Test Mock:**  
  Two tiers supported:
  1. **Tier 1 (Fastest / Zero-Dep):** `FakeVectorStore` python dictionary mapping `document_id -> {"embedding": vector, "metadata": metadata, "document": text}` with in-memory dot-product cosine ranking.
  2. **Tier 2 (Official Ephemeral):** `chromadb.EphemeralClient()` creating an isolated in-process memory database without disk persistence or network listening.

### Layer D: AI Resume Optimization Suggestions (LLM)
* **Real System Implementation:**  
  Prompt formatted with resume text and target job description; calls LLM endpoint or local fallback rule-engine.
* **Automated Test Mock:**  
  `MockSuggestionService` returns fixed, schema-compliant JSON payloads containing:
  * `improvements`: Array of concrete actionable resume bullet revisions.
  * `suggested_keywords`: List of recommended industry skills.
  * `readability_score`: Deterministic integer metric.
  * `generation_latency_ms`: Synthetic latency indicator.

## 3. Pytest Fixture Protocol & Reusability

All mocks are encapsulated into reusable pytest fixtures in `integration_omkar/tests/mocks/`:

```python
# Sample Usage in M3 Test Suites:
def test_resume_upload_with_mocked_storage(mock_storage):
    # 1. Arrange: Prepare mock file
    payload = b"%PDF-1.4 Mock PDF content"
    
    # 2. Act: Upload via fake storage
    result = mock_storage.upload_file(
        bucket="swipex-resumes",
        file_key="user_123/v1/resume.pdf",
        data=payload,
        content_type="application/pdf"
    )
    
    # 3. Assert: Deterministic verification
    assert result["success"] is True
    assert mock_storage.has_object("swipex-resumes", "user_123/v1/resume.pdf")
```

## 4. Verification & Non-Functional Guarantees (NFR Alignment)

| Criteria | Real Environment | Automated Test Harness |
| :--- | :--- | :--- |
| **Network Dependency** | Inter-container TCP (Docker bridge) | 100% In-Process / Local |
| **API Token Cost** | $0.00 (Self-hosted MinIO + ChromaDB) | $0.00 (Zero external calls) |
| **Model Download** | On image build / first execution | No model downloads required |
| **Test Suite Latency** | ~2–5s per full network roundtrip | < 10ms per unit / mock check |
| **Determinism** | Dependent on service startup timing | 100% Deterministic & Repeatable |
| **Offline Operation** | Requires running container engine | Fully runnable without internet or Docker |

This strategy ensures that GitHub Actions CI remains fast, reliable, and entirely green while teammate code develops in parallel.
